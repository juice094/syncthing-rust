# 注释与文档政策（2026-11 起施行）

> 本文件是 syncthing-rust 的唯一注释/文档标准。提交前改造与后续所有 PR 均按此执行。
> 背景：存量代码存在「一行代码一行注释」的行注释堆叠问题，且注释语言不统一，
> 对国际化贡献者构成门槛。本政策用「信息分层」替代「逐行解释」。

---

## 一、信息只走三个通道

| 通道 | 用途 | 语言 | 规则 |
|:---|:---|:---|:---|
| `///` / `//!` 文档注释 | 公开 API、模块职责、设计指针 | **仅英文** | 必填于所有 `pub` 项；模板见第二节 |
| `docs/design/` | 设计决策（ADR）、协议背景、流程时序图 | 决策记录中文 ADR + 英文摘要；时序图 Mermaid（语言中立） | 设计决策只落这里，不进代码注释 |
| `//` 行注释 | **原则上禁止** | — | 仅第三节列出的例外可存在 |

**删除对象**（改造时清除）：
- 复述下一行代码的 what-注释（`// 设置端口` 配 `set_port(...)` 之类）；
- `// =====...` 装饰分隔线、banner 块；
- 整段被注释掉的死代码（用 git 历史找回，不留在工作区）。

**迁移对象**（改造时搬入 `docs/design/`，代码内不残留）：
- 协议背景知识讲解段（BEP 握手流程、索引语义等）；
- 「为什么这么设计」的论证段 → 改写为 ADR（问题 → 备选方案 → 决定 → 理由）；
- 代码内保留指针的方式：在模块 `//!` 中加一行 `See "docs/design/<file>.md".`——**只允许通过 `//!`，不允许用 `//`**。

## 二、`///` 文档注释模板

```rust
/// One-sentence summary of what this does.（一句话说"做什么"）
///
/// # Errors（按需）
/// When/why this returns Err — 错误条件与含义。
///
/// # Panics（按需，仅当真实存在）
///
/// # Example（公共 API 建议给）
```

- 第一行以第三人称动词开头；不写「本函数/该方法」；
- 文档里说「为什么」仅限与调用者契约相关的部分；实现层论证放 ADR。

## 三、`//` 行注释的唯一例外

1. `unsafe` 块的 `// SAFETY:` 论证（项目红线要求）；
2. 算法/公式出处与外部参考（单行，含链接或文献标识）；
3. 临时 workaround，必须写成 `// TODO(#<issue>): ...`，指向 issue。

新增例外须先改本文件，不得在代码里自创类别。

## 四、时序图策略

- 凡描述「谁与谁按什么顺序交互」的内容（连接建立、Pull/Push 流程、删除防护、版本控制回滚），**统一用 Mermaid `sequenceDiagram`** 表达，替代散文步骤；
- 时序图源码存于 `docs/design/sequence/*.md`，被引用的文档内嵌同一份；
- 图内参与者/消息用英文标注（与代码符号同名），保证语言中立、任何语言读者可懂；
- 代码内禁止用注释复述时序图已表达的内容。

## 五、语言规则速查

| 位置 | 语言 |
|:---|:---|
| `///` / `//!` | 英文 |
| 例外 `//`（SAFETY/TODO） | 英文 |
| `docs/design/` ADR | 中文原文 + 头部英文摘要 |
| `docs/design/sequence/` 图内文字 | 英文 |
| `docs/dev/`（贡献者文档） | 英文为主，README 给中文链接 |

## 六、验收

- 改造以 crate 为波次提交，每波独立通过 fmt / clippy / test / doc / deny 五道门；
- 审查 checklist：无 what-注释、无 `// ====` banner、无死代码注释块、pub 项 `///` 覆盖率 100%（英文）、设计决策有 ADR 或 `//!` 指针。
