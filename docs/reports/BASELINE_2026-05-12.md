# Criterion Performance Baseline — 2026-05-12

> T-A1 完整基线（scanner + puller + bep encode/decode）  
> 平台: Windows 11, Rust 1.95.0, release+debuginfo (bench profile)  
> 报告: `target/criterion/`  
> 测量参数: warm-up 1s, measurement 2s, 30 samples（快速预览）  

> 注: 2026-05-11 的 scanner baseline 数据保留，本次新增 puller + bep encode/decode

## 1. Scanner SHA-256 块哈希（`syncthing-fs/benches/scanner.rs`）

> 来源: BASELINE_2026-05-11.md (重新归档)

| 文件大小 | 耗时 (median) | 吞吐量 (median) |
|----------|---------------|-----------------|
| 64 KiB   | 184.71 µs     | **338.37 MiB/s** |
| 1 MiB    | 654.61 µs     | **1.49 GiB/s** |
| 16 MiB   | 9.99 ms       | **1.56 GiB/s** |

**观察**: 大文件接近 SHA-256 硬件极限（~1.5 GiB/s），小文件受 I/O 开销限制。

## 2. Puller 单文件下载（`syncthing-sync/benches/puller.rs`）

> 使用 `ZeroBlockSource`（无网络/磁盘 IO 的模拟数据源），衡量纯 BEP 数据流处理

| 文件大小 | 耗时 (median) | 吞吐量 (median) |
|----------|---------------|-----------------|
| 1 KiB    | 532.26 µs     | 1.83 MiB/s |
| 1 MiB    | 669.95 µs     | **1.46 GiB/s** |
| 16 MiB   | 2.08 ms       | **7.51 GiB/s** |

**观察**:
- **1 MiB**: 与 scanner SHA-256 几乎一致（1.46 vs 1.49 GiB/s），puller 路径开销极小
- **16 MiB**: 接近内存复制极限（7.51 GiB/s），说明大块下载已完全 CPU-bound
- **1 KiB**: 500+ µs 主要为 tokio 任务调度 + DB lookup 开销

**优化空间**:
- 小文件（<64 KiB）路径可考虑批量化，减少 spawn 开销
- 大块路径已基本最优，无需进一步优化

## 3. BEP Hello Encode/Decode（`bep-protocol/benches/encode_decode.rs`）

### Hello 编码 / 解码

| 操作 | 耗时 (median) | 吞吐量 (median) |
|------|---------------|-----------------|
| `Hello::encode_to_vec()` | 237 ns | — |
| `Hello::decode(&bytes)`  | 135 ns | **507 MiB/s** |

### Round-trip (encode + decode)

| Payload 大小 | 耗时 (median) | 吞吐量 (median) |
|--------------|---------------|-----------------|
| 16 B    | 382 ns | 137 MiB/s |
| 64 B    | 370 ns | 265 MiB/s |
| 256 B   | 422 ns | 668 MiB/s |
| 1024 B  | 673 ns | **1.47 GiB/s** |

**观察**:
- prost 编解码效率符合预期（接近 protobuf-c 性能）
- 1 KB 已达 1.47 GiB/s，对 BEP 8KB block message 来说不会成为瓶颈
- 小消息（16-64 B）开销恒定（~370 ns），主要为系统调用 + 内存分配

## 4. T-B1: Rayon Parallel SHA-256 Validation

> 验证 rayon 并行化对 Scanner SHA-256 计算的实际收益。  
> Bench: `crates/syncthing-fs/benches/hash_parallel.rs`  
> 平台: Windows 11, 20 CPUs, 128 KiB block

### 加速比对照

| 数据量 | Blocks | Serial | Parallel | **Speedup** |
|--------|--------|--------|----------|-------------|
| 1 MiB | 8 | 482 µs → 2.02 GiB/s | 169 µs → 5.77 GiB/s | **2.85x** |
| 16 MiB | 128 | 7.65 ms → 2.04 GiB/s | 821 µs → 19.02 GiB/s | **9.32x** |
| 64 MiB | 512 | 31.9 ms → 1.96 GiB/s | 3.02 ms → 20.69 GiB/s | **10.56x** |
| 256 MiB | 2048 | 124 ms → 2.01 GiB/s | 10.8 ms → 23.17 GiB/s | **11.51x** |

### 关键观察

- **单线程吞吐稳定在 ~2 GiB/s**（SHA-256 单核硬件极限）
- **并行扩展近线性**：1MiB 仅 2.85x（8 blocks 不够分布式），但 16MiB+ 达 9-11x
- **20 核理论极限 ~14-15x**（考虑同步开销），实际 11.5x 接近理论上限
- **256 MiB 数据 10.8 ms 完成** vs 单线程 124 ms — 大文件首次扫描收益极大

### 结论

✅ **保留 rayon 并行化**，无需调整
- batch_size = 32 blocks 选择合理
- 专用线程池避免与 tokio I/O 争用

### 下一步建议

如要进一步优化：
- **SIMD/汇编 SHA-256**: 单核可进一步达 4-5 GiB/s（依赖 CPU 指令集）
- **批量哈希后台预热**: 在文件 mmap 时同时启动 hash 线程
- **磁盘 I/O 并行**: 当前是顺序 read 后并行 hash，I/O 可能成为新瓶颈
